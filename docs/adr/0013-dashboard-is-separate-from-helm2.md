# The dashboard is its own app, not a route in Helm 2.0

otto's dashboard is a Svelte app in `otto/dashboard/`, rather than a new route inside
Helm 2.0. Helm 2.0 is an append-only event log where thread state is a pure fold over
the log, and that architecture is load-bearing for what it does. A dashboard is a
read-through view over files, which would either corrupt that abstraction or bolt an
unrelated subsystem onto a repo that is currently green and is a portfolio piece.

## Consequences

- The two share no code, no tokens, and no visual identity. otto's dashboard is a
  full-screen instrument panel and Helm 2.0 is a phone client read in daylight; the
  same palette cannot serve both. What otto borrows is the *discipline*: semantic
  token names, theme switching by `data-theme`, and fixed scales. Not the values.
- Passkey authentication, when it is needed, is ported from Helm 2.0's
  `@simplewebauthn/server` setup rather than reinvented.

## Revised 2026-09-16

Three of this record's original consequences were wrong and are struck. The central
decision, that the dashboard is its own app, is unchanged.

- **"It shares Helm 2.0's design tokens, so the two look like one system."** Struck.
  Daniel never wanted this and said so. See the consequences above.
- **"Read-only panels can be static HTML regenerated by a routine, so most of the
  dashboard works with nothing running."** Struck. The dashboard is a live WebGL
  application that is iterated on visually. Generated static HTML is the cheapest
  thing that works and the worst thing to design against.
- **"The run endpoint stays loopback only, never behind `tailscale serve`."** The
  blanket rule is replaced by a split drawn where the risk actually is, because the
  headless run endpoint is deferred and may never be built. See ADR 0016.
